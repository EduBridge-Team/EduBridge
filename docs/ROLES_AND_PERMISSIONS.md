# الأدوار والصلاحيات في EduBridge

> آخر تحديث: 23 سبتمبر 2026  
> هذا المستند يصف الصلاحيات الفعلية المطبقة في الـ Laravel API والواجهة الحالية، وليس تصورًا نظريًا فقط.

## 1. الأدوار المعتمدة

| الدور | المفتاح | الوصف |
|---|---|---|
| ولي الأمر | `parent` | يدير أطفاله المرتبطين بحسابه ويتابع تقدمهم ودعمهم التعليمي. |
| المعلّم | `teacher` | يدير المحتوى التعليمي والواجبات والتقييمات للأطفال المسندين إليه. |
| الأخصائي | `specialist` | يدير الدعم التعليمي والجلسات والتقييمات وفريق الرعاية. |
| مدير النظام | `admin` | يمتلك صلاحيات الإدارة العامة والمراجعة والتوثيق وإدارة المستخدمين والأطفال. |
| الوزارة | `ministry` | تراجع المناهج والخطط التعليمية وتعرض الإحصاءات والبيانات المخصصة للوزارة. |
| المؤسسة التعليمية | `institution` | دور مؤسسي للوصول إلى دليل المستخدمين والبحث والوظائف العامة المصرح بها. |

## 2. قواعد عامة

جميع المسارات المحمية تتطلب JWT صالحًا عبر `auth.jwt`.

التحقق من الدور يتم في الخادم عبر `RoleMiddleware`، لذلك إخفاء زر في الواجهة لا يعتبر حماية بحد ذاته.

بعض الصلاحيات تعتمد على **الدور + ملكية/علاقة المورد**، مثل ملف الطفل أو تقييم درس أو ملف خاص.

الأدوار الحالية هي فقط:

```text
parent
teacher
specialist
admin
ministry
institution
```

## 3. صلاحيات مشتركة لكل مستخدم مسجل

كل مستخدم مسجل يمكنه، ما لم يوجد قيد إضافي في المسار أو داخل الـ Controller:

- عرض بيانات حسابه.
- تغيير كلمة المرور.
- رفع/حذف صورته الشخصية.
- حذف حسابه الشخصي.
- قراءة وتحديث إعداداته.
- استخدام مساعد نور ضمن حدود معدل الطلبات.
- استخدام نظام المحادثات بحسب الأطراف التي يسمح بها النظام.
- قراءة إشعاراته وتحديدها كمقروءة.
- رفع ملف خاص إلى التخزين الآمن.
- عرض ملف خاص مملوك له.
- عرض قائمة أنواع الإعاقة.
- عرض الدروس والبحث فيها وفتح تفاصيلها.
- عرض تقييمات الدروس وإضافة/تحديث تقييمه.
- حذف تقييمه الشخصي، بينما يستطيع الأدمن حذف أي تقييم.

## 5. الوصول إلى ملف الطفل

يطبق النظام طبقة إضافية عبر `ChildAccessMiddleware`.

### الأدمن
يستطيع الوصول إلى أي طفل.

### الأخصائي
يستطيع الوصول إلى ملفات الأطفال المحمية بهذا الـ middleware. وتوجد قيود أدوار منفصلة لبعض عمليات الكتابة الحساسة.

### المعلّم
يستطيع الوصول فقط إذا:

- كان `assigned_teacher_id` للطفل يساوي معرف المعلّم، أو
- كان المعلّم مرتبطًا بالطفل في جدول `child_teacher`.

كما يتم فلترة قائمة `/api/children` للمعلّم حتى لا يرى إلا الأطفال المسندين إليه.

### ولي الأمر
يستطيع الوصول فقط إلى الطفل المرتبط به في جدول `child_parent`.

### الوزارة والمؤسسة
لا تستخدمان ملف الطفل العام المحمي بـ `child.access`. الوزارة لديها مسارات عرض مخصصة.

## 6. بيانات الطفل الحساسة

حقول الهوية/التوثيق الحساسة للطفل تشمل:

- رقم هوية الطفل.
- رقم هوية ولي الأمر.
- مستند هوية ولي الأمر.
- مستند صلة القرابة.

هذه الحقول:

- تظهر للأدمن وولي الأمر المرتبط.
- يتم إخفاؤها عن بقية أفراد الفريق عند إرجاع بيانات الطفل.
- لا يستطيع تعديلها إلا ولي الأمر المرتبط أو الأدمن.
- عند تغيير بيانات التوثيق تعود حالة التوثيق إلى `pending` ما لم يحدد الأدمن خلاف ذلك.

## 7. الملفات الخاصة

### ملفات المستخدم

المسار:

```text
GET /api/private-files/user/{userId}/{filename}
```

يسمح بالوصول إلى:

- صاحب الملف نفسه.
- الأدمن.

### ملفات الطفل

المسار:

```text
GET /api/private-files/child/{childId}/{filename}
```

يسمح بالوصول إلى:

- الأدمن.
- ولي أمر مرتبط بالطفل فقط.

لا يستطيع المعلّم أو الأخصائي أو الوزارة أو المؤسسة فتح مستندات هوية/قرابة الطفل من هذا المسار.

## 8. التوثيق والمراجعة

### المستخدم العادي

يمكنه:

- إرسال بيانات هويته.
- قراءة حالة التوثيق الخاصة به.

### الأدمن فقط

يمكنه:

- عرض طلبات توثيق المستخدمين.
- قبول أو رفض توثيق المستخدم.
- عرض طلبات توثيق الأطفال.
- قبول أو رفض توثيق الطفل.
- استخدام مسارات التوافق القديمة لشاشة الأدمن.

## 9. إدارة المستخدمين

### الأدمن

يمكنه:

- عرض جميع المستخدمين.
- الفلترة حسب الدور.
- رؤية رقم الهوية في قائمة الإدارة.
- تعديل الاسم والبريد والدور والهاتف.
- حذف مستخدم آخر.
- لا يمكنه حذف حسابه بنفسه من مسار إدارة المستخدمين.

### ولي الأمر

في `/api/users` يرى جهات التواصل التعليمية فقط:

- المعلّمين.
- الأخصائيين.

ولا يرى أولياء الأمور الآخرين.

### المعلّم والأخصائي

تُعرض لهم جهات التواصل المسموحة من الفريق، مع استثناء الحساب الحالي.

### الوزارة والمؤسسة

يمكنهما قراءة دليل المستخدمين من المسار العام، مع إمكانية فلترة الدور، لكن بدون صلاحية تعديل أو حذف المستخدمين.

## 10. الدروس والمحتوى التعليمي

### إنشاء/تعديل/حذف الدروس

مسموح لـ:

- المعلّم.
- الأخصائي.
- الأدمن.

### مراجعة المحتوى

مسموح لـ:

- الوزارة.
- الأدمن.

### وسائط الدرس

إضافة وحذف الوسائط مسموح لـ:

- المعلّم.
- الأخصائي.
- الأدمن.

العرض متاح للمستخدم المسجل.

## 11. الدعم التعليمي والجلسات

### ولي الأمر

- ينشئ طلب دعم تعليمي.
- يعرض طلباته وفق نطاق الـ Controller.
- يستطيع إلغاء الطلب المسموح له.
- يعرض اجتماعات الدعم المتاحة له.

### الأخصائي والأدمن

- يعرضان الطلبات.
- يحددان الموعد والرابط.
- يكملان الطلب.
- يديران اجتماعات الدعم والجلسات.

### المعلّم

يمكنه عرض اجتماعات الدعم وبعض جلسات الطفل المسند إليه، لكنه لا ينشئ جلسة من مسارات الجلسات الحالية.

## 12. الوزارة

صلاحيات الوزارة الحالية تركز على الرقابة والمراجعة، ومنها:

- عرض الدروس المرسلة للمراجعة.
- قبول/رفض مراجعة المناهج.
- عرض المستخدمين عبر واجهة الوزارة.
- عرض الأطفال عبر واجهة الوزارة.
- عرض إحصاءات الوزارة.
- عرض مؤشرات التقدم الإحصائية.
- عرض طلبات الموافقة على الخطط.
- قبول أو رفض الخطط التعليمية.
- البحث برقم الهوية.

ولا تملك صلاحيات إدارة المستخدمين أو تعديل ملفات الأطفال من المسارات العامة.

## 13. المؤسسة التعليمية

الدور `institution` موجود كدور مستقل وله لوحة مستقلة في الموقع.

الصلاحيات الخلفية الحالية تشمل أساسًا:

- الوظائف المشتركة لكل مستخدم مسجل.
- قراءة دليل المستخدمين.
- البحث برقم الهوية.

ولا يملك حاليًا صلاحيات إدارة الأطفال أو المستخدمين أو مراجعة المناهج أو الخطط عبر المسارات الحالية.

## 14. ملاحظات أمنية مهمة

1. **الخادم هو مصدر الحقيقة للصلاحيات.** يجب عدم الاعتماد على الواجهة لإخفاء العمليات الحساسة فقط.
2. **الصلاحيات المرتبطة بالطفل يجب أن تستخدم `child.access`** كلما كان المسار يتعامل مع معرف طفل.
3. **المستندات الحساسة لا يجب تحويلها إلى روابط R2 عامة.** يجب أن تبقى خلف المسارات المصادق عليها.
4. **الوزارة والمؤسسة لا ينبغي أن تستخدما `/api/children` العام.**
5. عند إضافة Role جديد يجب تحديث:
   - قيد الأدوار في قاعدة البيانات/الموديل.
   - `RoleMiddleware`.
   - `edubridge-web/src/roles.js`.
   - `edubridge-web/src/roleRoutes.js`.
   - المسارات والـ Controllers ذات العلاقة.
   - اختبارات الصلاحيات.

## 16. قاعدة مختصرة عند تطوير ميزات جديدة

قبل إضافة أي Endpoint جديد، حدد بوضوح:

```text
من يستطيع تنفيذ العملية؟
هل يحتاج RoleMiddleware؟
هل المورد مملوك للمستخدم أو مرتبط بطفل؟
هل يحتاج child.access؟
هل يحتوي على بيانات حساسة؟
هل يجب أن يكون العرض فقط أم يسمح بالتعديل؟
هل يحتاج تسجيل Audit Log؟
```

يفضل اتباع مبدأ **أقل صلاحية ممكنة (Least Privilege)** وعدم منح دور صلاحية أوسع من حاجته الفعلية.
